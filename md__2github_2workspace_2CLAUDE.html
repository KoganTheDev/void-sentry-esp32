CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Void Sentry: ESP32-CAM (Freenove ESP32-WROVER, OV3660) pan/tilt turret that tracks motion via frame differencing and serves a web HUD. Arduino framework on PlatformIO.

Commands

All PlatformIO commands run from ESP32/. pio is not on PATH on this machine; use ~/.platformio/penv/Scripts/pio.exe (or the VS Code PlatformIO extension).

pio run -e freenove_esp32_wrover # build the turret firmware
pio run -e freenove_esp32_wrover -t upload
pio run -e pin_check -t upload # wiring bring-up test (no camera/WiFi), read serial after
pio device monitor # serial @ 115200, exception decoder enabled; type `wifi-reset` + Enter to erase saved WiFi networks and the PIN (reboots)
pio test -e native # host-side unit tests, no board needed
pio test -e native_sanitize # ASan+UBSan, Linux/CI only
pio test -e freenove_esp32_wrover -f test_wifi_manager # one on-device suite (board connected)
pio check --severity=high --severity=medium # cppcheck
python tools/tracking/make_synthetic_clips.py ESP32/bench/fixtures # regenerate synthetic clip fixtures (from repo root)
g++ -std=c++20 -O2 -g -Wall -Wextra -I ESP32/include -I ESP32/lib/tracking/include ESP32/lib/tracking/src/*.cpp ESP32/bench/track_bench.cpp -o track_bench # clip regression/bench, plain g++
./track_bench [--repeat N] ESP32/bench/fixtures/*.gray # exits non-zero if any .expect fails
python -m unittest discover -s tools/tracking -p "test_*.py" # fixture tool tests
  • Envs: freenove_esp32_wrover (firmware, excludes src/pin_check/), pin_check (only src/pin_check/), native (host gcc, tests under test/native/), native_sanitize (same tests under ASan+UBSan; Linux/CI only). Device envs ignore test/native/*; native only runs it.
  • Toolchain: Arduino core 3.3.12 via pioarduino 55.03.312 (ESP-IDF 5.5.5, GCC 14), C++20 everywhere (firmware, native, cppcheck locally and in CI). Core 3 passes -std=gnu++2b and -std=gnu++2a itself, so the firmware env build_unflags them and sets -std=gnu++20; native/native_sanitize use -std=gnu++20. The esp32-camera driver is bundled with core 3 (not a lib_dep). The platform is a GitHub release URL in platformio.ini.
  • custom_sdkconfig (in [env:freenove_esp32_wrover], inherited unchanged by pin_check): IDF 5.5 runs WebSocket handshakes through ws_pre/post_handshake_cb (the origin check and /stream viewer registration use them; handshake_guard.h has an #error if they are off), which the precompiled Arduino libs lack, so pioarduino rebuilds the libs with them plus 80 MHz flash/PSRAM clocks (board_build.f_flash = 80000000L). The first build after a clone or any change to that text is slow (20-40 min); it is then cached in ~/.platformio keyed on the exact custom_sdkconfig text, so both firmware envs must keep identical text or each env switch rebuilds. It generates gitignored files in ESP32/: sdkconfig.freenove_esp32_wrover, sdkconfig.pin_check, sdkconfig.defaults (CI caches it with ~/.platformio), CMakeLists.txt, dependencies.lock, .dummy/, managed_components/. The partition table is the project copy partitions_min_spiffs.csv (core 3 binary is ~1.14 MB, too big for the default 1.25 MB slot; NVS offsets are unchanged so saved WiFi and calibration survive). If a package error mentions FRAMEWORK_DIR None, run pio pkg install -e <env> from PowerShell.
  • native uses the first g++ on PATH and needs GCC >= 10 (C++20). This machine has WinLibs GCC 14.2 + LLVM 19 (clang-format, clangd) from winget, but an old MinGW 6.3 at C:\MinGW\bin may still shadow it. Check g++ --version if native builds fail on C++20. Code under test there must not include Arduino/ESP-IDF headers.
  • On-device suites under ESP32/test/ are Unity sketches (setup() calls UNITY_BEGIN()), flashed and read over serial. Several are placeholders or stale: test_motion/test_servo.cpp (targets a Turret::Servo class that no longer exists) and test_joystick/test_joystick.cpp (passes 150 as the button pin and includes "Joystick.h" with the wrong case for Linux).
  • Never pipe pio into something that exits early (grep -m1, head): on Windows pio blocks forever writing to the closed pipe and the build looks hung. Redirect to a log file and grep the file. A clean firmware build takes about 1 minute.
  • Serial port is the CH340 (COM3 or COM4 - the number changes when the board is re-plugged; check pio device list). To read the board without resetting it, open the port with DTR/RTS held low.
  • Formatting: .clang-format (LLVM base, Allman braces for functions/classes/control statements, 4-space indent, 120 columns, int* p), clang-format 19 locally (WinLibs LLVM) and in CI (pip install "clang-format==19.1.*"). A Claude Code PostToolUse hook (.claude/hooks/format_cpp.py) formats firmware C/C++ files on edit. CI (ci.yml) only checks with --dry-run --Werror and never commits to the branch.
  • CI (ci.yml): format, web-ui-generator, build (one job: freenove_esp32_wrover and pin_check, caching ~/.platformio and ESP32/sdkconfig.defaults), native-tests, native-sanitize and tracking-bench (fixture tool tests, fixtures regenerated and cmped byte-for-byte, clip regression under ASan+UBSan, cachegrind instructions/frame, perf stat best effort). ci.yml also has workflow_dispatch for manual runs. cppcheck stays in static_analysis.yml.
  • CI static analysis (static_analysis.yml) runs cppcheck with --error-exitcode=1 --std=c++20 and blocks on warning/performance/portability findings. Use // cppcheck-suppress <id> inline when a finding is intentional.
  • Doxygen (ESP32/Doxyfile) publishes to gh-pages on push to main. Public headers use Doxygen @brief/@details blocks; keep that style for new APIs.
  • Board logs: Arduino's logger only shows ESP_LOGx from files that include esp32-hal-log.h (or Arduino.h); pure ESP-IDF files must include it or their logs are silently dropped.

Sanitizers and profiling

Use them throughout the project, on the target where each one actually works:

  • ASan + UBSan, host only. Any logic that can be native-tested must also pass under -fsanitize=address,undefined -fno-omit-frame-pointer (the native_sanitize env, run as a CI job on Ubuntu). New pure-logic modules are designed so they can run there. Never weaken a test to silence a sanitizer report; fix the bug.
  • Not on Windows. The MinGW toolchains here (WinLibs GCC 14 and Clang 19) ship no libasan or libubsan (cannot find -lasan, verified). Decision: CI is the sanitizer and host-benchmark runner. No local WSL/Linux setup, so don't suggest installing one. Push and read the CI job output instead.
  • Not on the ESP32. There's no ASan for Xtensa. On-device memory safety is covered by design (no per-frame allocation, bounded buffers) and by watching heap_min and psram_min in the serial stats line.
  • perf, host only (Linux, so it runs in CI). It can't profile the ESP32. GitHub's shared runners make absolute timings noisy, so compare runs within the same job, or use instruction counts (perf stat -e instructions) rather than wall time. Use it for host-side benchmarks of algorithm code (for example Stage 2 frame-diff detection run on recorded frames): perf stat for totals, perf record -g + perf report for hot spots, built with -O2 -g -fno-omit-frame-pointer.
  • On-device profiling: time code sections with esp_timer_get_time() (microseconds), use ESP.getCycleCount() for very short sections, and report per-stage averages in the periodic stats line rather than logging per frame (logging itself distorts timing).
  • Benchmarks are reproducible: each perf-relevant change records its method and numbers (fps, latency median, heap_min) in the PR description.

Required local setup

  • Stage 6: the firmware no longer includes or needs ESP32/include/secrets.h to build (WiFi is provisioned on the device, see Architecture), and CI no longer copies the template. The file and its .example still exist until the user removes them after saving their network in NVS; until then the rules in this paragraph stay. secrets.h is gitignored. Never commit it, read it, or print its contents. This is enforced: .claude/settings.json denies Read/Edit on **/secrets.h, and .claude/hooks/guard_wifi_credentials.py blocks any shell command containing the substring secret (so ask the user for anything involving that file, including copying the template; put commit messages that mention it in a file and use git commit -F). The hook is an accident guard, not a security boundary. On-device WiFi provisioning is implemented in Stage 6; these rules are relaxed in a follow-up once the user has removed the file.
  • The project's Claude Code hooks (.claude/settings.json) invoke python; on a machine that only has python3 they exit 127, which fails open (the WiFi-credential shell guard then does nothing).

Architecture

Frames are produced by a camera FreeRTOS task, analysed by a dedicated detection task and pushed to viewers by a stream task. loop() runs controller.run() → WifiManager::maintain() → log_stream_stats() and yields 1 tick each pass; it does no detection. All objects are globals constructed in src/main.cpp and wired by reference (manual dependency injection).

  • Controller (lib/controller) depends only on interfaces: BaseDetectionModule and BaseTurret, plus Joystick (not Camera or FrameStore). Modes are ControlMode {Ai, User, Calibrate} (system_control_types.h, wire names ai|user|calibrate). The Z button goes through aiming::ButtonClassifier: a short press toggles Ai/User (or records a calibration point in Calibrate), a long press (1.5 s) enters Calibrate or cancels it and restores the previous mode. User and Calibrate jog at 25 Hz without needing frames; detection runs continuously in its own task in every mode, Ai reads the track snapshot every pass and feeds it to the aim policy, and Calibrate reads it for calibration points. Mode toggles call detection.reset(), which is only a request flag. Controller implements BaseStatusProvider and publishes a ControlStatus (mode, calibration state, pose) under a spinlock for /commands.
  • Detection and tracking: JPEG frames go jpeg_gray (1/8-scale decode to 40x30 gray: DC-only, no IDCT, ~7 ms measured versus ~71 ms at 1/4 scale, so one cell = 8x8 QVGA pixels; decoder is the vendored C TJpgDec in lib/tjpgd, not the ROM copy, which is ~40% slower; keep it at the default -Os, -O2 measured 3x slower) -> tracking::MotionDetector -> tracking::Tracker. The lib/tracking library is pure (no Arduino headers) and natively tested. CameraDiffDetection (lib/detection, implements BaseDetectionModule) is the glue: a pipeline allocated once in internal RAM (~12.6 KB; tracking 0.6 ms there versus 1.1 ms in PSRAM) that runs decode + detect + track on its own "detect" task (start_task(FrameStore&), core 1, prio 3, 4096 B stack; woken by FrameStore::publish, processes the newest unseen frame, 200 ms wait timeout) and publishes a track snapshot under a spinlock, which /commands reads for the HUD. detect_object's direction return is unused for aiming: the camera is fixed, and aiming::AimPolicy maps the track snapshot position through the calibrated AimMap to absolute pan/tilt targets for the motor task. TestDetection is a stub.
  • Remote control (lib/remote, pure and natively tested): remote::parse turns a /commands text message into a Command; remote::RemoteInbox keeps the latest Move (300 ms dead man, jog speed 0.6) and a pending mode request. Controller::submit (httpd task) stores into the inbox under its own spinlock; Controller::run takes the mode request every pass and arbitrates jog input in User/Calibrate (button held in Calibrate -> stop, deflected stick, else HUD jog, else stop) at 25 Hz.
  • Aiming and movement (lib/aiming pure and natively tested, lib/motion device): the camera is fixed on the base and the turret aims absolutely, so image pixels map to pan/tilt angles through a fixed two-point linear AimMap (aim_map.h). AimPolicy turns the tracker's pixel position into Aim/Home/Hold commands (deadband, home after the target is lost). BaseTurret/Turret take set_target_deg(), jog() and home() as non-blocking mailbox writes; a motor task drives the 28BYJ-style stepper (yaw, own coil driver) and servo (pitch). Calibration: hold the button 1.5 s, aim at a spot near one corner and short-press, then the opposite corner; CalibrationSession fits the map and cal_store saves it in NVS (namespace aim, key map, CRC-checked blob), loaded by Controller::begin() at boot. Without a saved map the default map is used and the HUD shows UNCALIBRATED.
  • Camera frame ownership: a camera FreeRTOS task (lib/frame_store/src/camera_task.cpp, core 1, prio 4) copies each driver frame into one of 4 fixed 32 KB PSRAM slots in FrameStore and returns the driver buffer immediately. Bookkeeping is the pure frames::FrameSlots (natively tested); readers hold move-only RAII frames::FrameLeases, and a leased slot is never rewritten (a new frame is dropped and counted instead). No per-frame allocation anywhere on the frame path. Frames are JPEG (needed for streaming), QVGA, CAMERA_GRAB_LATEST; incomplete JPEGs (no FF D8 ... FF D9) are dropped as corrupt. PSRAM is mandatory. FrameStore wakes up to 2 subscribers (stream task, detect task; add_subscriber/remove_subscriber, fixed atomic slots, no heap) with xTaskNotifyGive on every publish.

Task layout (Stage 4: core 1 is camera copy + detection + control, core 0 is network + motor + the camera driver; httpd is pinned to core 0 so network bursts cannot preempt detection):

  • WiFi provisioning (Stage 6; pure lib/provisioning namespace prov, device glue in lib/network): up to 3 networks saved in NVS (namespace wifi, keys nets, pin, appw; CRC-checked blobs). prov::WifiPlan is the connection state machine (Boot/Scanning/Joining/Connected/Lost/Setup) and returns actions; WifiManager (global instance in main.cpp) executes them with the Arduino WiFi API. begin() returns at once and maintain() (from loop()) never blocks: async scanNetworks(true), WiFi events only set atomic flags (processed in maintain()), one FreeRTOS mutex guards the list, PIN guard, scan cache and plan state shared with httpd. With no saved network in range (or 120 s lost) it opens a WPA2 hotspot VoidSentry-XXXX (192.168.4.1, 10 random chars password from esp_random, printed on serial only when setup mode starts) with a DNS catch-all; a successful join stops the hotspot after a 10 s grace period. lib/network/wifi_http.cpp serves /wifi (generated wifi_html.h), /api/wifi/status|scan|saved, POST /api/wifi/add|forget (the Host header must be an IPv4 literal on all /api/wifi/* requests, against DNS rebinding; POSTs are also origin-checked; 256 B form body read under a 3 s overall deadline, then 408; a present but invalid password is a 400, only a missing key means an open network; one shared PinGuard: 5 wrong PINs lock out, and the lockout is RAM-only, so a reboot resets it and needs physical access or a crash; a first PIN is accepted only while the hotspot is up or nothing is saved) and the catch-all GET /* (302 to /wifi in setup mode, and / redirects there too while the hotspot is up). The HttpServer uses httpd_uri_match_wildcard, so the catch-all must be registered last. Never log or return passwords or the PIN.
  • Network (lib/network): HttpServer wraps ESP-IDF esp_http_server (not the Arduino WebServer). Endpoints: / (gzipped HUD page), /stream WebSocket, /commands WebSocket (replies to every message with JSON motion metrics). The HUD sends move:<dir> (up, down, left, right and the four diagonals, resent every 100 ms while held), move:stop, mode:ai|user and fire:on|off on /commands; the handler parses each message with remote::parse (fixed 64 B receive buffer, a longer or non-text frame closes the session) and hands it to the Controller as a remote::BaseRemoteSink. Moves jog in User and Calibrate (ignored in Ai; while the button is held in Calibrate the jog is zero), expire 300 ms after the last one (dead man, so a dropped connection stops the turret), and the joystick wins over a HUD jog; fire is parsed but not acted on. The HUD mode button toggles Ai/User and is ignored (dropped, never deferred) during calibration; calibration itself stays joystick-only (hold 1.5 s enters or cancels it, a short press records a point). The joystick button still toggles modes too. Browser pages from another origin are refused at the WebSocket handshake of /commands and /stream (remote::origin_allowed: when an Origin is present it must equal http(s):// + Host and the Host must be an IPv4 literal with optional port, which defeats DNS rebinding since the board is always reached by IP; a missing Origin is allowed); non-browser LAN clients are not authenticated - LAN auth is a known follow-up. Handlers are static C callbacks, so instances reach state through static members / user_ctx. /stream is a push WebSocket: StreamBroadcaster wakes on each published frame and, for each idle viewer (max 2, frames::ViewerSet), queues one send onto the httpd task (httpd_queue_work + httpd_ws_send_frame_async); busy viewers skip frames, which keeps latency low. close_fn removes viewers and must close the socket. WiFi modem sleep is disabled for latency, httpd send_wait_timeout is 2 s, and the HUD sends a 1-byte keepalive on /stream every 2 s (push-only viewers would otherwise be LRU-purged) and reconnects on close.
  • move_types.h / system_control_types.h in ESP32/include/ are shared value types (MoveX, MoveY wrap enum class with to_string() and implicit uint8_t conversion).
  • Benchmark stats: main.cpp logs [stream] up= captured= sent= dropped_no_slot= oversize= corrupt= viewers= copy_us_avg= heap= heap_min= psram= psram_min= decode_us_avg= track_us_avg= scene_changes= decode_fail= track= id= mode= pan= tilt= steps_s= motor_late= motor_stack_free= aims= jpeg_b_avg= every 5 s, followed by a second line [detect] det_frames= dec_win_us= trk_win_us= det_stack_free= idle0= idle1= rssi= wifi= (two lines because the ROM printf behind Arduino logging truncates a line after about jpeg_b_avg, which used to cut the window fields off; det_stack_free is the detect task stack high-water mark in bytes, sampled every 100 frames; idle0/idle1 are the share of 1 kHz tick samples (percent, last 5 s window) that found each core in its IDLE task - tick sampling is kept for continuity with the Stage 4 numbers (core 3 does enable CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS, so vTaskGetRunTimeStats is now an option); this is how core 0 saturation shows before the task watchdog (which watches IDLE0 only) reboots the board; rssi is the WiFi signal in dBm; wifi is the connection plan mode (sta|setup|joining|lost); det_frames is frames analysed in the last 5 s window (about 83 at full rate), dec_win_us/trk_win_us are per-frame decode and detector+tracker averages over that same window, 0 if no frames - unlike the since-boot _avg fields they show a slowdown as it happens; jpeg_b_avg is the mean JPEG size in bytes over the last 5 s window, 0 if no frames; decode_us_avg/track_us_avg are per-frame averages in microseconds, track is the tracker phase; motor_late counts motor-task wake-ups lagging more than 1 tick, motor_stack_free is the motor task stack high-water mark in bytes, aims counts Aim commands sent to the turret); heap_min/psram_min drifting down means a leak.
  • Tracking fixtures (ESP32/bench/fixtures/): <name>.gray is concatenated 1200-byte frames (40x30, row-major, 8-bit gray). <name>.expect is key=value lines (# comments) with optional keys lock_by_frame, max_ids, min_locked_frames, min_scene_changes, max_scene_changes, no_track_after_frame=N (tracker Idle on every frame from N to the end - the ghost check); a malformed line fails the clip and a missing .expect only warns; track_bench fails when an expectation is violated. The real_*.gray clips are recorded on the board (committed, not generated); the generator only writes the four synthetic ones, and CI's cmp step iterates over its output. Detector rules from those clips: a scene change needs both >35% foreground AND a frame-mean shift > 25 (a close person covers 35-45% of the grid but auto-exposure holds the mean), and warm-up (17 frames) copies the frame into the background so exposure settling and lamp afterglow do not become ghosts. seed_object and pause_leave are the ghost clips: the detector's fg_age_limit = 34 (a cell foreground for more than 34 consecutive frames goes back to the fast background rate) makes ghosts of a wrong background clear in ~3 s instead of ~14 s. The synthetic clips are generated by tools/tracking/make_synthetic_clips.py (deterministic, CI checks they are up to date). Record real clips with tools/tracking/record_stream.py <board_ip> <seconds> <dir> (needs pip install websockets) then tools/tracking/jpeg_to_gray.py <dir> <out.gray> (needs Pillow), and write a .expect for them.

Pin constraints

include/pins.h is the only place GPIOs are defined (turret and camera). Its static_asserts reject flash/PSRAM pins (6-11, 16, 17), camera collisions, duplicates, non-ADC1 joystick axes and the stepper on GPIO0. The map is verified on hardware; don't change it without a reason.

  • With the camera attached exactly 8 GPIOs are free (0, 2, 12, 13, 14, 15, 32, 33) and the turret uses all 8. The stepper sits on strapping pins 12/15/2, which is safe only because ULN2003 inputs pull low.
  • GPIO12 high at reset selects 1.8V flash -> boot loop with invalid header: 0xffffffff, and uploads fail with Wrong boot mode detected (0x2b). Seen on this build when the ULN2003's +/- were reversed (it then leaks current out of its IN pins and energizes every coil, so the motor gets hot). In the ROM's boot:0x.. value, bit 5 is GPIO12, bit 4 is GPIO0.
  • Wiring is on a breadboard via the Freenove GPIO Extension Board, which feeds USB 5V/GND to the left rails and 3.3V/GND to the right rails. Motors run from the left 5V rail.
  • Camera XCLK is 12 MHz, not the usual 20 MHz. Measured on this board 2 m from the router (ping avg / 14 KB page fetch / capture fps): 20 MHz = 265 ms / 1.1-5.0 s / 27.8 fps (WiFi crippled); 16 MHz = 27 ms / 0.1-2.4 s erratic / 17.8 fps; 12 MHz = 19 ms / 0.07-0.13 s / 16.6 fps; 10 MHz = 17 ms / 0.14-0.19 s / 13.8 fps; camera off = 10 ms / 0.07 s. Higher XCLK means more camera clock/DMA activity that degrades WiFi; 12 MHz is the best fps that keeps WiFi healthy. Also: DHCP may give the board a new IP after reflashing - read the IP from the boot log, never assume it.
  • JPEG quality is 18 (camera.h, was 12): at 12, close-up or noisy scenes made QVGA frames 2.5-4x bigger, which doubled the JPEG decode time on the detection path (decode cost scales with bytes) and loaded WiFi. Watch jpeg_b_avg in the stats line (measured 2026-10-13).

Web UI pipeline

  • Edit web/web_ui.html only. ESP32/lib/network/include/index_html.h is generated and gitignored: web/update_index_html.py (a PlatformIO pre: script) runs before compilation and writes it via web/html_header.py, only when the content changed. Gzip uses mtime=0 so the output is deterministic.
  • python -m unittest discover -s web -p "test_*.py" tests the generator (also run in CI).
  • /commands is request/reply: the HUD polls with " " and the board answers every message with one JSON reply. All HUD sends go through App.sendCommand(), and the next poll is scheduled only when no message is awaiting its reply, so exactly one poll loop runs. Never schedule a poll from a reply without that check: the old HUD sent fire:off on every unlocked reply, each reply started another loop, the loops doubled every round trip, and httpd saturated core 0 until the task watchdog rebooted the board (Stage 4, measured with idle0). The same storm running on core 1 (httpd was unpinned then) is the likely cause of the Stage 3 "detection slows when a person sits close" symptom.
  • web/compress_HTML_to_C_header.py / decompress_C_header_to_HTML.py are standalone manual converters, not part of the build.
